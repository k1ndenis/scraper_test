# Books Scraper API

FastAPI-сервис, который асинхронно собирает каталог [Books to Scrape](https://books.toscrape.com/), сохраняет книги и категории в PostgreSQL и предоставляет HTTP API для просмотра данных и истории запусков.

## Быстрый запуск через Docker Compose

1. Создайте файл с переменными окружения:

```bash
cp .env.example .env
```

2. Соберите образы и запустите PostgreSQL и приложение:

```bash
docker compose up --build -d
```

3. Примените миграции базы данных:

```bash
docker compose exec app alembic upgrade head
```

4. Убедитесь, что сервис доступен:

```bash
curl http://127.0.0.1:8000/health
```

Остановка сервисов:

```bash
docker compose down
```

Данные PostgreSQL хранятся в named volume `postgres_data`; команда `down` его не удаляет.

Для запуска без Docker также нужны Python 3.12 и доступный PostgreSQL. Скопируйте `.env.example` в `.env`, задайте в нём параметры этой БД (в частности, для PostgreSQL на той же машине замените `POSTGRES_HOST=db` на `POSTGRES_HOST=127.0.0.1`), установите пакет (`pip install .`), выполните `alembic upgrade head` и запустите `uvicorn app.main:app --reload --host 0.0.0.0 --port 8000`.

## Тесты

Установите зависимости для разработки:

```bash
pip install -e '.[dev]'
```

Затем запустите тесты. Интеграционным тестам нужен PostgreSQL с применённой схемой; передайте асинхронный DSN в `TEST_DATABASE_URL`:

```bash
TEST_DATABASE_URL='postgresql+asyncpg://books_user:books_password@127.0.0.1:5432/books_db' pytest
```

Без `TEST_DATABASE_URL` интеграционные тесты будут пропущены. Модульные тесты можно выполнить отдельно:

```bash
pytest -m 'not integration'
```

Дополнительно настроен GitHub Actions: на каждый `push` и `pull request` workflow использует Python 3.12, поднимает PostgreSQL, применяет миграции и запускает `ruff check .` вместе с полным `pytest`, включая интеграционные тесты через `TEST_DATABASE_URL`.

## API

Интерактивная спецификация доступна в [Swagger UI](http://127.0.0.1:8000/docs).

| Метод и путь | Назначение |
| --- | --- |
| `GET /health` | Проверка работоспособности приложения. |
| `POST /scrape` | Создаёт запуск сбора и ставит задачу в фон. Возвращает `202 Accepted`. |
| `GET /scrape-runs` | Список запусков сбора. |
| `GET /scrape-runs/{run_id}` | Один запуск и его статистика. |
| `GET /books` | Список книг с фильтрами и пагинацией. |
| `GET /books/{book_id}` | Одна книга. |
| `GET /categories` | Список категорий с числом книг. |

У списочных endpoints параметры `limit` (по умолчанию `20`, от `1` до `100`) и `offset` (по умолчанию `0`). `GET /books` дополнительно принимает `search`, `category`, `min_price`, `max_price`, `rating` (1–5) и `in_stock`.

Примеры:

```bash
# Проверка сервиса
curl http://127.0.0.1:8000/health

# Запустить сбор. Ответ, например: {"run_id": 1, "status": "pending"}
curl -X POST http://127.0.0.1:8000/scrape

# Проверить статус конкретного запуска
curl http://127.0.0.1:8000/scrape-runs/1

# Получить книги с фильтрами и пагинацией
curl -G http://127.0.0.1:8000/books \
  --data-urlencode 'search=light' \
  --data-urlencode 'min_price=10' \
  --data-urlencode 'rating=3' \
  --data-urlencode 'in_stock=true' \
  --data-urlencode 'limit=20' \
  --data-urlencode 'offset=0'

# Категории и история запусков
curl 'http://127.0.0.1:8000/categories?limit=20&offset=0'
curl 'http://127.0.0.1:8000/scrape-runs?limit=20&offset=0'
```

Ответ списка содержит `items`, `total`, `limit` и `offset`. Статус запуска может быть `pending`, `running`, `success` или `failed`; его ответ также содержит счётчики обработанных категорий и книг, созданных/обновлённых книг, ошибок и возможное сообщение ошибки.

## Архитектура

Приложение разделено по слоям:

```text
app/
├── api/           HTTP-роуты, валидация параметров и зависимости FastAPI
├── schemas/       Pydantic-схемы запросов и ответов
├── services/      сценарий запуска скрейпинга и учёт его состояния
├── scraper/       HTTP-клиент, обход каталога, парсинг и параллельная загрузка книг
├── repositories/  запросы к БД, фильтрация и сохранение сущностей
├── db/            SQLAlchemy-модели, engine и сессии
├── config.py      настройки из окружения
└── main.py        композиция FastAPI-приложения
```

`api` не содержит бизнес-логики: он передаёт работу сервисам и репозиториям. Слой `services` координирует сценарий, `scraper` получает и преобразует внешние HTML-данные, а `repositories` изолирует доступ к PostgreSQL. Используются FastAPI, SQLAlchemy async и драйвер `asyncpg`.

## Скрейпинг: асинхронность и надёжность

Страницы товаров загружаются конкурентно через `httpx.AsyncClient`; общий `asyncio.Semaphore` ограничивает число одновременных HTTP-запросов **10**. Для сетевых ошибок и ответов 5xx выполняется до трёх попыток с экспоненциальным backoff: 0,5 с, затем 1 с. Ошибки 4xx не повторяются. Ошибки отдельных карточек фиксируются в статистике запуска и не останавливают обработку остальных книг.

Сетевой клиент отделён от чистого HTML-парсера: парсер получает готовую строку HTML и URL, поэтому его можно проверять на сохранённой HTML-фикстуре без сети.

Сохранение идемпотентно по уникальному `UPC`: при первом появлении книги создаётся запись, при повторном запуске существующая книга обновляется только если её данные или категория изменились. Если изменений нет, запись остаётся нетронутой и не учитывается как обновлённая.

Для выдачи API выбрана offset pagination (`limit` + `offset`): она проста для клиентов, позволяет перейти к известному смещению и естественно сочетается с ответом, содержащим общее `total`. Для текущего объёма каталога её недостаток — замедление на очень больших смещениях — несущественен; при большом и часто изменяемом наборе данных предпочтительнее cursor pagination.

## Фоновый запуск и ограничение

`POST /scrape` сначала сохраняет `ScrapeRun` со статусом `pending`, а затем передаёт обработку `FastAPI BackgroundTasks`. Это позволяет немедленно вернуть `202 Accepted` и `run_id`, не удерживая HTTP-соединение во время обхода каталога, и не требует отдельной очереди задач для данного небольшого сервиса.

`BackgroundTasks` выполняются в процессе веб-приложения, поэтому это намеренно не является надёжной очередью: при падении или перезапуске приложения задача будет потеряна. Если к этому моменту запуск уже переведён в `running`, запись может остаться в этом статусе. Для production-устойчивости потребовались бы внешняя очередь и worker (например, Celery/RQ) и механизм восстановления зависших запусков.

## Результаты E2E-проверки

Полный запуск на целевом каталоге дал:

- 1000 книг;
- 50 категорий;
- 0 ошибок.

Повторный запуск создал 0 и обновил 0 книг, что подтверждает идемпотентность. `POST /scrape` вернул `202 Accepted` примерно за **0,036 секунды**.

## Ограничения и не реализовано

- Нет надёжной фоновой очереди, перезапуска задач и автоматического восстановления запусков со статусом `running`.
- Нет аутентификации, авторизации, rate limiting и наблюдаемости уровня production (метрик, трассировки, централизованных логов).
- Нет cursor pagination: текущая offset pagination сознательно выбрана для небольшого каталога.
- Нет отдельного endpoint для отмены запущенного сбора.

## Фактическое время выполнения

Около **6 часов**, включая разработку, тесты, рефакторинг, E2E-проверку и документацию. Наибольшую трудность вызвало новое для меня извлечение данных из HTML: пришлось изучить структуру каталога и карточки книги, подобрать CSS-селекторы, обработать относительные URL, цену, остаток, рейтинг и отсутствующие поля.
